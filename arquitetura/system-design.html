Semanas 6–8 — System design

Um sistema por semana, 45 min cronometrados, falando em voz alta. Antes do primeiro desenho: recitar o glossário. Se travar, não desenhe ainda.

Walkthrough guiado (45 min) — encurtador, depois o mesmo relógio no pagamento

O quadro abaixo é o cronômetro. Aqui está a aula já falada, para você sentir o ritmo antes de gravar o áudio sozinho.

Minutos 0–10 — perguntas e números (encurtador)

O que você precisa entender. Quem sai desenhando caixa perde. Quantos redirects/s? Quantos creates/s? URL customizada? TTL? Latência do redirect (isso é o p99 que importa)? Consistência: dois usuários podem ganhar o mesmo código curto?

Exemplo concreto. 100 M redirects/dia ≈ 1,2k QPS médio, pico 10× → ~12k QPS leitura. Creates 1% disso. Código de 7 chars na base62. Redirect p99 < 20 ms. Código único é invariante: não pode duplicar.

Agora você (2 min). Escreva três perguntas que o entrevistador ainda não fez e que mudam o desenho (região única? analytics em tempo real?).

Minutos 10–25 — API, dado, caixas

Exemplo já desenhado. POST /links (idempotente por body hash ou chave do cliente) devolve https://x/{code}. GET /{code} 302. Tabela code → url longa + created_at no Postgres no começo; cache Redis no GET (cache-aside, TTL com jitter). Hash do código: geração em serviço (range de IDs ou hash + retry em colisão). Leitura pesada: cache + réplicas. Sharding pela chave code quando a escrita de create e o volume de linhas exigirem — não no dia 1 com 12k QPS só de GET se o cache segura.

Minutos 25–45 — aprofundar e o que quebra

Aprofunde cache stampede no código famoso, hot key (um link viral), colisão de código, TTL vs link eterno, multi-região (código gerado em duas regiões). Trade-off: Redis na frente do 302 vs consistência do create (Postgres único até o QPS de escrita pedir shard).

O mesmo relógio no processador de pagamento (item 5 da tabela): 5 min de requisitos (idempotência, p99 do “pago”, consistência do saldo); 5 min QPS; API POST /pagar com Idempotency-Key; dado = ledger no serviço dono; alto nível = gateway → checkout → outbox → Kafka → faturamento com inbox; aprofunde saga e DLT; gargalo = hot key do cliente-vip e retry sem jitter.

Agora você. Cronometre 45 min no encurtador em voz alta. Depois no pagamento, sem olhar este walkthrough — só o quadro de minutos.

Framework de resposta (45 min)

MinBlocoO que o arquiteto faz

Sem o glossário na ponta da língua (latência, p99, CAP, quando não microsserviço), o desenho vira teatro. Recite antes.

Perguntas-síntese (as que mais aparecem)

  • Descreva a arquitetura do sistema em que você trabalha hoje, com os trade-offs, em 3 minutos. A abertura mais comum em entrevista sênior. Precisa estar ensaiada.
  • Qual foi a decisão de arquitetura mais difícil que você tomou e por quê?
  • Conte um incidente de produção que você resolveu — da detecção ao post-mortem.
  • O que você faria diferente se recomeçasse o projeto atual?
  • Como você convence o time a adotar (ou a não adotar) uma tecnologia nova?
  • Um serviço está com p99 de 3 segundos. Descreva sua investigação passo a passo.
  • Como você garante que um sistema distribuído não perca dado?
  • Eventual vs inconsistente — dê um exemplo de cada no seu domínio.

Checklist de fluência (60 segundos)

  • Arquitetura = decisão cara de reverter
  • Latência vs throughput vs p99
  • CAP só durante partição; PACELC no dia a dia
  • Eventual ≠ invariante quebrada
  • Timeout primeiro na resiliência
  • Quando não microsserviço
  • Banco por serviço; Outbox; Saga
  • Log / métrica / trace
  • System design: perguntar requisitos antes de desenhar
