Vocabulário

Partição

O que é. Cada partição é um log independente em disco: uma sequência de segmentos (arquivos .log + índices) no broker líder. Offset 0, 1, 2… só existe dentro daquela partição. O líder recebe o ProduceRequest; os followers copiam. Num consumer group, cada partição é atribuída a no máximo um membro — por isso 1 partição = 1 trabalhador ativo naquele grupo.

Analogia: as colunas do caderno. Cada coluna é um caderninho com ordem própria.

Para que serve. Escala (mais colunas → mais consumidores em paralelo), distribuição entre brokers, ordem local (só dentro da coluna — a key escolhe a coluna).

Na prática. Conferir as três colunas:

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe --topic pedidos.criados

Você deve ver PartitionCount: 3 e três linhas Partition: 0, 1, 2 com o líder. No Java:

TopicBuilder.name("pedidos.criados")
    .partitions(3)
    .replicas(1)
    .build();

No lab. TopicConfig.java e lab.partitions: 3 em application.yml. Aula completa de alterar partições: Partições e grupos.

Aumentar partições depois recalcula hash(key) % N com N novo: o pedido 99 pode mudar de coluna e a ordem histórica daquela entidade quebra. O Kafka não diminui partições. Mais partições = mais arquivos, réplicas, memória e rebalance mais caro.

Sessão 1 — Fila vs caderno

O que você precisa entender. Na fila clássica, pegar o recado o tira da fila. No Kafka o recado continua no caderno. Quem lê só move a marca “já li até aqui”. Dois times podem ter marcas em linhas diferentes no mesmo caderno — e isso é o desenho certo, não um bug.

Exemplo concreto. O tópico pedidos já tem linhas. No desenho compacto abaixo, na partição 0 o faturamento parou no offset 0 e o analytics já foi até o 2. Num caderno grande a mesma ideia vira números de plantão: faturamento no offset 80, analytics no 12 — ou o contrário. As duas marcas estão certas. O caderno não apaga a linha; um grupo atrasado não impede o outro.

Pegadinha. “Analytics já leu, então faturamento não vê mais o PedidoCriado A.” Falso. A linha 0 continua lá. Só a marca laranja ainda não passou dela.
Agora você (5 min). Feche a página. No papel: quem escreve, três colunas, duas marcas em offsets diferentes na coluna 0. Se as marcas ficarem na mesma linha “porque é mais limpo”, a analogia da fila ainda está no comando.

Sessão 2 — As cinco palavras no pedido 99

O que você precisa entender. Evento é o fato. Tópico é o caderno. Partição é a coluna. Offset é o número da linha naquela coluna. Key escolhe a coluna e, com isso, a ordem daquela entidade.

Exemplo concreto. O checkout publica PedidoCriado do pedido 99, key = 99, eventId estável. O recado cai na partição 1, vira offset 4. Depois sai PagamentoAprovado do mesmo 99 — mesma key, mesma coluna, offset 5. Analytics e faturamento leem esses dois recados na ordem 4 → 5 nessa coluna. Pedido 40 pode estar na partição 0 no offset 4: é outro recado; o número 4 não é global.

Pegadinha. Publicar sem key “para espalhar carga” no fluxo do pedido 99. Os recados Criado / Pago / Enviado podem cair em colunas diferentes; o consumidor pode ver Pago antes de Criado.
Agora você (5 min). Escreva uma frase para cada palavra usando só o pedido 99. Se aparecer “offset é o ID da mensagem no cluster”, volte no caderno.

Sessão 3 — Réplica e o desenho resolvido

O que você precisa entender. O broker guarda o caderno. Cada partição tem um líder (quem recebe o append) e seguidores. ISR = quem está em dia. acks=all espera o ISR; não cobra cartão por você. Retenção apaga página velha; compaction deixa só a última linha de cada key.

Exemplo concreto. Tópico pedidos, 3 partições. Grupo A (faturamento) sobe 4 consumidores. Grupo B (analytics) sobe 1. Abaixo está o desenho já resolvido — não é exercício em branco.

Na mesma coluna, A pode estar no offset 80 e B no 12. As marcas não brigam. A key pedido-X permanece na mesma coluna enquanto o número de partições não muda.

Pegadinha. “Subo o 4º pod do faturamento e o lag cai.” Sem 4ª partição, o 4º consumidor fica olhando o teto. Outra: achar que acks=all impede cobrança duplicada — isso é a aula de garantias.
Agora você (5 min). Redesenhe de memória: 3 colunas, A1–A4, B1. Marque o ocioso. Se A4 ganhar uma fatia, o modelo ainda não colou.

Mão na massa — criar e alterar partições

O que é, no cluster. --partitions 3 cria três logs. O Spring do lab faz o mesmo com TopicBuilder. Alterar para 6 muda o módulo da key: o pedido 99 pode sair da coluna em que estava.

Suba o Compose, crie (ou descreva) o tópico:

cd labs/kafka
docker compose up -d

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --if-not-exists \
  --topic pedidos.criados \
  --partitions 3 --replication-factor 1

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe --topic pedidos.criados

No Java (já está no repo — não copie para outro projeto):

@Bean
NewTopic pedidosCriados() {
  return TopicBuilder.name("pedidos.criados")
      .partitions(3)
      .replicas(1)
      .build();
}

Só depois de produzir com key 99 e anotar a partição, experimente (isso quebra a cola histórica):

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --alter --topic pedidos.criados --partitions 6

No lab. TopicConfig.java, README seção “Cria o tópico”. Produce: POST /pedidos?pedidoId=99&comKey=true com o pedido-service no ar. Dois grupos no mesmo log: lab 3 na aula Spring.

Não diminua partições: a API do Kafka não oferece --partitions 2 depois de 3. Recriar tópico apaga o caderno.

Quiz depois da aula. Abra, responda sem olhar, só então leia a explicação.

Kafka é uma fila de mensagens?

Não. É um log em que só se acrescenta no fim, fatiado em partições e replicado. A mensagem não some quando é lida. Ela expira por tempo, por tamanho, ou some na compaction. Cada grupo mantém o próprio cursor. Por isso dá para reprocessar, dá para vários leitores independentes, e a leitura não é destrutiva. Na fila clássica, em geral a mensagem é entregue e retirada.

O que é um evento, e o que deve ir nele?

Um fato imutável, com nome (PedidoCriado), um identificador estável (eventId — essencial para não processar duas vezes), a key de particionamento (pedidoId), timestamp, e o estado necessário para o consumidor agir sem ligar de volta — ou só o ID, se for notificação. Não coloque destinatário. Quem se importa se inscreve no tópico.

O que é uma partição e por que ela existe?

Unidade de paralelismo, de ordenação e de replicação. Throughput de escrita e de leitura (por grupo) escala com o número de partições — e é limitado por ele. “Um consumidor por fatia” também nasce daqui.

Offset, committed offset e auto.offset.reset

Offset = posição na partição. Committed = até onde o grupo jura que já processou. auto.offset.reset só vale quando ainda não há commit: earliest relê desde o início ainda retido; latest ignora o passado e cola no fim (stream ao vivo). Escolher latest num job que deveria reprocessar histórico é bug silencioso.

Kafka garante ordem?

Só dentro de uma partição. Não existe ordem global no tópico. Se a ordem importa para uma entidade, use a mesma key — ela cai na mesma partição enquanto o número de partições não muda. “Ordenados” significa: o consumidor vê a sequência de append no líder. Dois produtores no mesmo pedido ao mesmo tempo: a ordem é a de chegada, não a do relógio.

Como funciona um consumer group?

Cada partição é atribuída a exatamente um consumidor do grupo. Grupos diferentes recebem cópias independentes. Mais consumidores que partições = ociosos. Escalar consumo exige aumentar partições — e aumentar partições redistribui keys (quebra ordenação histórica). Decida cedo.

O que é o ISR? E acks?

ISR = réplicas em dia com o líder. Combinado com acks=all e min.insync.replicas=2, a mensagem foi replicada antes de ser confirmada. Se o ISR cair abaixo do mínimo, o produtor recebe erro — melhor do que perder dado em silêncio. acks=0: máximo throughput, pode perder. acks=1: o líder gravou, o follower pode não ter. acks=all: durabilidade de verdade.

Retenção e log compaction

Retenção apaga segmentos antigos. Compaction mantém a última mensagem por key. O tópico passa a representar o estado atual, não o histórico. Não é backup. Tombstone (value nulo) pede para apagar a key.

Producer, consumer, broker — uma frase cada

Broker guarda o log e replica. Producer appenda no líder da partição. Consumer lê o log e move o próprio offset. O Kafka não executa a sua regra de negócio.

Exercício de papel (não pule). Desenhe um tópico com 3 partições, 2 grupos, 4 consumidores no grupo A e 1 no grupo B. Grupo A: no máximo 3 trabalham, 1 fica ocioso. Grupo B: o único lê as 3 partições (sozinho, em loop). Offsets independentes: A pode estar no 80 e B no 12 na mesma coluna. Marque um pedido com key pedido-X sempre na mesma coluna.
