Sessão 1 — As peças antes do lab

O que você precisa entender. Spring é fiação. KafkaTemplate escreve. @KafkaListener lê com um groupId. concurrency é quantas mãos no mesmo crachá — o teto é o número de partições. AckMode é quando a marca anda. Serializer quebrado sem handler vira poison pill.

Exemplo concreto. Tópico pedidos com 3 partições. concurrency = 6 (ou 6 pods): três threads trabalham, três olham o teto. Listener com auto-commit: a marca pode andar antes da cobrança do 99. Manual depois do efeito: morte no meio relê o 99 — lab 7.

Pegadinha. Copiar YAML com concurrency 8 porque “o notebook tem 8 cores”. A conta é min(concurrency × instâncias, partitions).
Agora você (5 min). Sem abrir o lab: escreva o que você espera ver no log quando publicar 9 mensagens com keys pedido-1/2/3. Só então rode os labs 1–3.

Labs 4–9 continuam nas sessões 2 e 3: mate processo, veja ocioso, veneno, duplicata, outbox com broker morto, lag e hot key. A aula acima é o mapa; os nove laboratórios abaixo são o chão.

As peças do Spring, em linguagem de leigo

O Spring não muda o Kafka. Ele só é a fiação: quem escreve, quem lê, quantas mãos no caderno, quando a marca anda.

KafkaTemplate — quem escreve

Analogia: a caneta da sua aplicação. Você diz tópico, key e value; o template serializa e manda para o líder da coluna.

É o produtor. template.send("pedidos.criados", pedidoId, evento). A key no segundo argumento é a que escolhe a partição. Sem key, o Spring/cliente espalha — e a ordem por pedido some. Trate erro de send: “mandei” não é “o ISR confirmou”. Com acks=all você espera a confirmação; ignore isso e o checkout mente para o usuário.

@KafkaListener — quem lê

Analogia: a pessoa do time com o crachá group.id, olhando a coluna que o Kafka atribuiu.

O método anota “quando chegar recado neste tópico, rode isto”. O groupId é o crachá. Mude o groupId e você lê o caderno de novo, da sua própria marca. Dá para receber o objeto já desserializado ou o ConsumerRecord cru (aí você imprime partition, offset, key — obrigatório nos labs).

concurrency — quantas mãos no mesmo crachá

ConcurrentKafkaListenerContainerFactory cria N consumidores no mesmo grupo. Cada um pode ficar com partições. O teto é o número de partições. concurrency = 6 num tópico de 3 partições deixa 3 threads olhando o teto. O número que importa é min(concurrency, partitions). Subir replica no Kubernetes é a mesma conta: 8 pods × tópico de 3 partições = 5 ociosos.

AckMode — quando a marca anda

BATCH: o Spring commita o lote depois de processar (rápido; morte no meio = replay do lote). RECORD: commita cada recado (mais chatice, menos replay). MANUAL / MANUAL_IMMEDIATE: você chama ack depois do efeito — o lugar certo se cobra cartão. Auto-commit ligado no consumer factory é o atalho que perde mensagem. Nos labs de duplicata, use manual de propósito.

Serializer, ErrorHandlingDeserializer, RetryableTopic

  • Serializer / deserializer: transforma objeto ↔ bytes. JSON é didático. Avro/Protobuf + Schema Registry é o que time grande usa.
  • ErrorHandlingDeserializer: JSON quebrado não deve derrubar o listener inteiro. Sem isso, a poison pill vira loop de crash.
  • RetryableTopic / DefaultErrorHandler + DLT: tenta de novo com espera; depois manda para o tópico cemitério. Erro permanente ≠ timeout de banco.
Narrar em voz alta antes de rodar: “eu espero ver as 9 keys pedido-1/2/3 cada uma numa coluna só”. Se o resultado surpreender e você não souber por quê, o lab falhou mesmo com o teste verde.

Os nove laboratórios (coração da trilha)

O listener já imprime partition, offset, key, value, group. Sem isso no log você está voando cego.

Lab 1 · Anatomia

Ver as colunas de verdade

Abrir. Compose + pedido-service. Tópico: TopicConfig (3 partições).

Rodar. Sem key, depois com key:

curl -s -X POST "http://localhost:8080/pedidos/lote?comKey=false&n=9"
curl -s -X POST "http://localhost:8080/pedidos/lote?comKey=true&n=9"

Olhar. Log do PedidoConsumer: sem key as linhas saltam de partition; com pedido-1/2/3 cada key cola numa coluna. Offsets 0,1,2 da partição 0 não são os da partição 1.

Arquivos. PedidoController /pedidos/lote, PedidoProducer.publicar(..., comKey).

Lab 2 · Ordem

O mesmo pedido, com e sem key

Rodar. Três eventos do 99, rápido, primeiro comKey=false, depois true:

for s in 1 2 3; do curl -s -X POST "http://localhost:8080/pedidos?pedidoId=99&comKey=false"; done
for s in 1 2 3; do curl -s -X POST "http://localhost:8080/pedidos?pedidoId=99&comKey=true"; done

Olhar. Sem key, faturamento e analytics podem intercalar colunas. Com key, a sequência daquela entidade permanece na mesma partition.

Lab 3 · Dois grupos

Dois crachás, o mesmo caderno

Já está no app. PedidoConsumer tem groupId = faturamento e analytics.

Rodar. Um lote com key. Olhar. Os dois logs imprimem as mesmas 9 linhas; as marcas são independentes:

docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group faturamento --describe
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group analytics --describe
Lab 4 · Rebalance

Matar o processo e ver a pausa

Rodar. Com o consumer no ar, Ctrl+C no Spring e suba de novo. Olhar. Logs revoked / assigned. Durante o rebalance clássico o Fetch para. concurrency: 3 no YAML = três membros no grupo faturamento.

Arquivos. application.yml (listener.concurrency, max.poll.interval.ms).

Lab 5 · Ociosos

Gente demais para pouca coluna

Rodar. Mude spring.kafka.listener.concurrency para 6, reinicie. Tópico continua com 3 partições. Olhar. Três threads sem assignment. A conta é min(concurrency, partitions) por grupo.

Lab 6 · Poison pill

Payload que o deserializer não engole

Rodar. Console producer no tópico (JSON quebrado, sem schema id). Sem error handler o listener daquela partição grita o mesmo erro. Com Schema Registry, payload inválido nem passa no serializer do POST /pedidos — por isso o veneno aqui é o console:

docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic pedidos.criados
# cole: {quebrado

Depois volte ao producer Spring (payload válido) e veja as outras colunas andarem. DLT de verdade é a aula de operação + DefaultErrorHandler no seu serviço — o lab mostra a coluna travada sem handler.

Lab 7 · Duplicação

Ack depois do efeito

Abrir. PedidoConsumer.faturamento: o ack.acknowledge() está no fim. Coloque um System.exit(1) (ou kill -9) depois do log e antes do ack, publique o 99, mate, suba. Olhar. O recado volta (at-least-once). Inbox não está neste método — é o exercício: tabela eventId unique na mesma transação do pagamento.

Arquivos. ack-mode: manual no YAML; enable-auto-commit: false.

Lab 8 · Outbox

Kafka desligado, pedido salvo

Rodar.

docker compose stop kafka
curl -s -X POST "http://localhost:8080/pedidos/outbox?pedidoId=outbox-1"
# H2: pedido existe. OutboxPublisher tenta e a linha fica pendente.
docker compose start kafka
# em ~2s o poller publica

Arquivos. OutboxService (mesma transação pedido + outbox), OutboxPublisher (@Scheduled 2s), POST /pedidos/outbox.

Lab 9 · Lag e partição quente

Atraso visível, depois uma coluna só

Rodar. Muitos produces com keys espalhadas, depois 90% com a mesma key:

curl -s -X POST "http://localhost:8080/pedidos/lote?comKey=true&n=90"
# depois: muitas vezes pedidoId=vip
for i in $(seq 1 80); do curl -s -X POST "http://localhost:8080/pedidos?pedidoId=vip&comKey=true"; done

docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --group faturamento --describe

Olhar. Lag por partição. Hot key: uma coluna com CURRENT-OFFSET atrasado, as outras em dia. Subir concurrency não drena a coluna do vip.

Critério de pronto desta aula. Você explica cada lab sem abrir o código, e aponta o trecho desta página (partição, offset, grupo, DLT, outbox, lag) que o lab ilustra. Teste verde sem narrativa não conta.
