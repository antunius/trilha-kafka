Sessão 1 — O filme do rebalance

O que você precisa entender. O grupo pausa para redistribuir colunas quando alguém entra, sai, perde heartbeat ou estoura max.poll.interval.ms. Durante o rebalance clássico, ninguém lê. O loop: lote lento → broker acha que morreu → rebalance → recomeça o lote → de novo.

Exemplo concreto. Três pods no grupo faturamento, três partições. O pod A1 está cobrando um lote de 500 recados e cada cartão leva 200 ms. Passa max.poll.interval.ms sem um poll novo. O coordenador tira A1, redistribui P0. A2 e A3 também param enquanto a dança acontece. A1 volta, o lote recomeça — e estoura de novo.

Pegadinha. Subir mais pods para “sair do rebalance”. Mais membros = mais dança se o lote continua lento. A correção é lote menor, trabalho mais rápido, intervalo maior, ou membership estático no restart planejado.
Agora você (5 min). Desenhe o ciclo em quatro caixas. Marque onde CooperativeSticky e group.instance.id doem menos — não onde “eliminam” o problema.

Sessão 2 — Lag e a coluna quente

O que você precisa entender. Lag alto em todas as colunas ≠ lag numa só. Doze consumidores em três partições não criam doze leitores paralelos: só três trabalham. Partição quente: uma key (um cliente enorme) empilha numa coluna; as outras zeradas.

Exemplo concreto. Produção 2_000 recados/s, consumo 400/s em cada uma das 3 colunas saudáveis — lag sobe nas três. Ou: 90% das keys são cliente-vip → P1 no 50_000 de lag, P0 e P2 em zero. Escalar o Deployment para 12 réplicas não drena P1.

Pegadinha. Olhar lag total do grupo e “dar scale”. Se for uma coluna só, scale é teatro.
Agora você (5 min). Escreva a ordem: produção vs consumo; dependência lenta; hot key. Só então “mais partições”.

Sessão 3 — Veneno vs timeout, depois DLT

O que você precisa entender. JSON quebrado é permanente: tenta N vezes e vai para o tópico cemitério, senão aquela coluna trava para sempre. Timeout de banco é transitório: retry com espera; mandar para o DLT perde o pedido 99 de verdade.

Exemplo concreto. Offset 40 da P0 é {quebrado. Sem DLT o listener grita o mesmo erro; P1 e P2 podem seguir. Com DLT o 40 vai para pedidos.DLT e a marca da P0 anda para 41. Outro dia o Postgres oscila 2 segundos: isso não é veneno — é retry.

Pegadinha. Um ErrorHandler que manda qualquer exception para o DLT. Você enterrou cobrança recuperável.
Agora você (5 min). Duas linhas: “vai para DLT” vs “retry”. Coloque JSON inválido, schema incompatível, 500 do cartão, timeout do banco, 400 de regra de negócio.

Rebalance: o que dispara e por que dói

Entrada/saída de consumidor, queda de heartbeat, ou estouro de max.poll.interval.ms. Durante o rebalance clássico, o consumo para.

Loop clássico: o lote demora mais que o intervalo máximo de poll → o broker acha que o consumidor morreu → rebalance → o processamento recomeça → ciclo. Correções: reduzir max.poll.records, acelerar o processamento, ou aumentar o intervalo. Também vale checar se o pod foi morto por falta de memória.

Para doer menos: assignor cooperativo (redistribui sem parar tudo), membership estático (group.instance.id evita rebalance em restart planejado), processamento rápido. Heartbeat em thread separada já é o padrão do cliente moderno.

Lag crescendo: ordem do diagnóstico

  1. O consumo ficou mais lento ou a produção aumentou?
  2. O gargalo está no consumidor ou numa dependência (banco, API)?
  3. Há partição quente por key mal distribuída?

Ações: mais partições + mais consumidores, processar em lote, tornar o trabalho assíncrono onde possível, ou escalar a dependência. Aumentar consumidores sem aumentar partições não resolve nada.

Produtor: o que realmente importa

  • acks — 0 perde escrita; 1 o líder gravou; all espera o ISR. É durabilidade, não consumo.
  • enable.idempotence — retry do mesmo producer não duplica no log.
  • retries + delivery.timeout.ms — até quando insistir. Sem teto, o send fica preso para sempre.
  • linger.ms e batch.size — esperar uns milissegundos junta envelopes. Sobe throughput, sobe latência.
  • compression.type lz4/zstd — menos bytes na rede e no disco.
  • max.in.flight.requests.per.connection — com idempotência, até 5 ainda preserva ordem na partição.

Consumidor: o que realmente importa

  • max.poll.records — tamanho do lote. Lote enorme + processamento lento = rebalance.
  • max.poll.interval.ms — quanto tempo você pode ficar sem “oi, ainda estou vivo e processando”.
  • session.timeout.ms / heartbeat.interval.ms — o pulso. Heartbeat some → o grupo acha que você morreu.
  • auto.offset.reset — earliest para pipeline/histórico; latest para “só o ao vivo”. Só vale sem commit prévio.
  • fetch.min.bytes / fetch.max.wait.ms — esperar um pouco para buscar mais linhas de uma vez.
  • enable.auto.commit — quase sempre você quer controle manual no serviço de negócio.

Dead Letter Topic (DLT) e poison pill

Mensagem que falha depois de N tentativas vai para um tópico separado, em vez de travar a partição para sempre (a “pílula venenosa”: um payload inválido no meio da coluna).

Erro permanente (JSON quebrado) → DLT direto. Erro transitório (banco fora) → retry com espera crescente. Mandar erro transitório para o DLT perde dado. Ficar tentando erro permanente trava a partição.

Como monitorar e o que é partição quente

Olhe: lag por partição, taxa de rebalance, tempo de processamento, taxa de erro e volume no DLT. Alerte em lag crescente e sustentado, não em um pico de um segundo. Offset parado numa partição só = poison pill ou hot key.

Partição quente: uma coluna recebe muito mais tráfego que as outras (um cliente enorme, ou key constante). Sintoma: lag só nela, as outras em zero. Kafka não rebalanceia carga dentro da partição. A correção é redesenhar a key (cuidado com ordem) ou splittar o trabalho depois da leitura.

Mini-runbook (cole no Notion do time)

  1. Lag em todas as partições: produção subiu ou o consumidor ficou lento? Olhe o banco/API. Só então pense em mais partições.
  2. Lag numa partição só: poison pill (erro no log) ou hot key. Não “dá scale” no grupo inteiro.
  3. Consumidores restartando: max.poll, OOM, deploy sem static membership.
  4. DLT enchendo: payload mudou? Schema incompatível? Ou alguém mandou timeout de banco para o cemitério?

Se você não consegue seguir essa ordem num incidente simulado, a aula de operação não fechou — config decorada não opera cluster.
